1) Быстрые ответы на твои главные вопросы

Почему раньше в Network было "всё есть", но на оффере пусто?

Потому что тест-оффер 5171 читает параметры только из URL-строки (window.location.search), а не из POST-body. Если форма отправила данные в Form Data, но не в URL, этот оффер их не увидит.

В 5171_offer_archive/index.php прямо стоит: const params = new URLSearchParams(window.location.search);.

Что такое Query String и Form Data простыми словами?

  • Query String — часть URL после ?, например ?sub_id_24=Ivan&sub_id_27=a%40b.com.
  • Form Data — тело POST-запроса (body), не всегда дублируется в URL.
  • Если оффер/скрипт читает только Query String, то Form Data "не видна" для него.

Почему было дублирование параметров в DevTools?

Потому что один и тот же набор sub_id добавлялся в URL (Query String) и одновременно как поля формы (Form Data). Для тестового GET-оффера это избыточно и сбивает визуально.

Что значит Display GET Params (5171)?

Это демонстрационный оффер-страница, которая выводит то, что пришло в URL как GET-параметры, и подсвечивает, какие обязательные параметры отсутствуют.

Почему после первого фикса у тебя мог быть 404?

Вероятная причина (инференс): редирект ушёл на невалидный/неподставленный URL (например, шаблон вида {offer}) или на некорректно собранный action. В итоговом рабочем варианте добавлены проверки URL перед редиректом (setKeitaroOfferAction возвращает false, если URL плохой).

5.2 Что делает form-handler в 4051

Отдельный form-handler.js берёт форму #mForm, валидирует, собирает значения, и строит финальный URL редиректа.

Функции

  • validate() — проверка email/phone.
  • findFirstInvalid() — фокус/анимация первой невалидной ячейки.
  • setKeitaroOfferAction(form) — сбор URL с query-параметрами из формы.
  • waitOn(btn) — блокировка кнопки на момент отправки.

Итоговый принцип

  • Берём window.KT.offerUrl.
  • Пробегаем все поля формы через new FormData(form).
  • Пишем их в url.searchParams.set(...).
  • Делаем window.location.href = actionUrl (query-only).
4051_landing_archive/form-handler.js:76-108
function setKeitaroOfferAction(form) {
  const offerUrl = window.KT && typeof window.KT.offerUrl === 'string'
    ? window.KT.offerUrl
    : '';

  if (!offerUrl || offerUrl.includes('{offer}') || offerUrl.includes('%7Boffer%7D')) {
    return false;
  }

  if (!/^https?:\/\//i.test(offerUrl)) {
    return false;
  }

  let actionUrl = offerUrl;
  try {
    const url = new URL(offerUrl, window.location.origin);
    const formData = new FormData(form);

    for (const [name, value] of formData.entries()) {
      if (name === '_lp' || name === '_token') continue;
      if (typeof value !== 'string') continue;
      if (value.trim() === '') continue;
      url.searchParams.set(name, value);
    }

    actionUrl = url.toString();
  } catch (e) {
    actionUrl = offerUrl;
  }

  form.setAttribute('action', actionUrl);
  return true;
}

7) Инцидент 4051: последовательный разбор "почему было так"

Шаг 1. Симптом

На оффере (Display GET Params) пусто по обязательным полям, хотя в Network ты видишь sub_id в запросе.

Шаг 2. Технический факт

В Network может быть одновременно:

  • Query String Parameters (в URL),
  • Form Data (в POST body).

Оффер 5171 проверяет только Query String через window.location.search.

Шаг 3. Почему дублировалось

Код мог одновременно прокинуть sub_id через URL и hidden input-поля формы, из-за чего в DevTools появлялись дубли в query и body.

Шаг 4. Что было сделано в рабочем решении

  • Значения формы собираются через FormData(form).
  • Но вместо POST body они сериализуются в URL query (url.searchParams.set).
  • Далее идёт редирект window.location.href = actionUrl.
  • Итог: query содержит все sub_id, 5171 их видит.

Шаг 5. Почему первый фикс мог дать 404

Это не 100% доказанный факт, а рабочая гипотеза: редирект улетал на некорректный action URL. В текущем решении добавлены защитные проверки на placeholder {offer} и валидность URL.

8) Практический чек-лист дебага (когда пишут "не прилетают параметры")

Шаг A. Проверка на лендинге

  • Открой DevTools → Network → запрос отправки.
  • Смотри Request Method.
  • Смотри отдельно: Query String Parameters и Form Data.
  • Проверь, есть ли ключевые sub_id: 24,25,27,26,22,23,21,9.

Шаг B. Проверка целевого оффера

  • Если оффер типа 5171 (GET display), то поля обязаны быть именно в Query String.
  • Если оффер серверный и читает POST, тогда Form Data может быть достаточной.

Шаг C. Проверка action URL перед отправкой

  • Проверь, что не осталось {offer} в сыром виде.
  • Проверь, что URL абсолютный (http:// или https://).
  • Проверь, что в конце нет сломанного query из-за двойных ?/&.

Шаг D. Keitaro-side sanity

  • Кампания активна.
  • Поток ведёт на нужный landing и нужный offer.
  • Домен/HTTPS в статусе OK (если нужен динамический tracking method).
Быстрый smoke-test: временно ставишь оффер 5171, отправляешь форму, видишь все обязательные поля — значит client-side часть передачи исправна.

10) Словарь терминов простым языком

Термин Что значит
Landing Страница-прокладка/квиз, где пользователь взаимодействует до оффера.
Offer Целевая страница/партнёрка/CRM endpoint, куда приводится пользователь/данные.

Финальная памятка по твоему кейсу

Если тестируешь через 5171 → отправляй данные в Query String. Network смотри по двум блокам: Query и Form Data отдельно. Валидация и транспорт данных — разные уровни, проверяй оба. Невалидный offer URL почти всегда = риск 404.
